## 1. 判断待ち(タブの行は既存のまま・**バッジだけ 2026-10-29 変更**)

- データ元: `~/.local/state/toposai/confirm_box/events-*.jsonl` の箱 + `pending_user_decisions.jsonl` の未投函 + Paseo の承認待ち。
- バッジ(**2026-10-29 変更**): **窓口Aがいま出せる件数**(`confirmBoxCountRpc.presentable`。
  permit は足さない=窓口の答えを画面側で書き換えない)。判定は判断窓口の Python(`judgment_window.py badge-count` =
  `presentable_left`。窓口の選び出し `claim_next` そのものを dry で呼ぶ)1か所だけで、
  Paseo 側は数字を読むだけ(`server/presentable-count.ts`)。窓口は1問ずつなので1=次の `next` が1件返す /
  0=出せるものがない。**0 のときはバッジを出さない**。バッジは**読むだけ**で、押して開いても件を
  先取りしない(`commit` 経路は 2026-10-29 の出口レビューで外した: `claim_next` は抱えた件の期限を
  上書きするので、押すと窓口Aが持っている件の期限が縮む。数字は1/0なので先取りの利点も無い)。
  実際に出す1件は窓口Aが選ぶ。承認待ち(permit)は数字に入れない: 窓口は permit を出さないので、
  画面側で足すと窓口の答えを書き換え、既に一覧にある permit の行を二重に数えることになる
  (出口レビュー1巡目 指摘3・2巡目 指摘3)。TS 側の集合(`open`)で 0 を確定しもせず、窓口が読める限り
  Python に聞く(2巡目 指摘1)。
  旧版は open 総数 N を数えていたため、裏方が検討中の件まで数えて「バッジ2件なのに窓口Aは出せるものがない」
  (逆に「開くとカードがあった」)が起きた(2026-10-28 ユーザー「そしたらバッジださないでよ」)。
  `countJudgmentCounted`(open 総数)は一覧の「判断待ち」の数としては残るが、バッジには使わない。
- 数え切れないとき(判断ノートを読めない・見えない・Python が答えない)は件数の代わりに「!」を出す
  (`presentable: null`)。0 件を「判断待ちなし」と読ませないため。
- 判断タブの行の既定の絞り込みは `isJudgmentOpen`(判断印 or permit の `state: "new"`)で、**N より行が
  多いことがある**。まだノートになっていない投函も画面から消さないため(数える側だけ N に揃える)。
  数える対象(N)は行の対象の部分集合。サイドバーのバッジ(`presentable`)は窓口の答えなので、
  N の集合とは一致しないことがある(抱えたままの件・検討中の件など)。ノートの無い古い行は一覧に残るが、
  答え先が無いので、片付けは箱へ ack を書く(運用)。
